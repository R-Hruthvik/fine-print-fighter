Positioning research

Requirements to become an evidence-first dispute assistant

The app should prepare, check, and cite a user-reviewed dispute record. The user alone sends, files, and tracks it externally. This report combines external best practices, an internal readiness audit, and a prioritized requirement set.

1. Is the app ready now?

Substantially yes. It never sends or files anything; analysis is transient unless the user explicitly saves; evidence is traceable but applicability remains deliberately unresolved; compensation is separated from entitlement; and disclosures are pervasive. Main gaps: unattainable strong ratings, stale test fixtures, and minor export/citation and accessibility verification gaps.

2. External requirements for this positioning

  • Framing: state plainly that the tool is informational, not a law firm, not affiliated with government/ombudsman/regulator; distinguish legal information from legal advice; define scope and when it cannot help.
  • Evidence: preserve originals; maintain chain-of-custody metadata and hashes; redact only release copies; support user-controlled retention/deletion/export.
  • Privacy: data minimization, purpose limitation, lawful basis/consent, transparency, security, privacy by design, right to erasure, layered plain-language notice.
  • Accessibility: WCAG 2.2 AA; multiple channels; plain language; support for representatives/assistive needs.
  • User control: explicit consent; review/edit before external use; self-service export/correction/deletion; user-driven escalation.
  • Escalation: tiered ladder with prerequisites, timelines, documented company attempt, preserved complaint trail, deadlines that close routes.
  • Disclaimers: visible, plain-language, aligned with actual practices; “not legal advice,” “informational purposes only,” consult a professional.
  • Must not: no complaint-filing service framing, no attorney-client relationship, no outcome promises, no auto-submission without review/consent, no fabricated or altered evidence.

3. Prioritized requirements

Must-have

  • M1 Restore release baseline: build, lint, tests pass; fix cacheComponents conflict, native link, test alias, stale fixtures.
  • M2 Sign-aware numeric grounding.
  • M3 Resolve letter citations from actual letter text.
  • M4 Enforce applicability ceiling in code and docs.
  • M5 Minimize PII in search queries.
  • M6 Retain/display only HTTPS sources.
  • M7 Make company-response and exhibit handling consistent.
  • M8 Make Rebuttal Lab limits and grounding consistent.
  • M9 Validate saved-case input and identifiers.
  • M10 Keep remedy as request, not entitlement.
  • M11 Correct documentation drift.

Should-have

  • S1 Applicability review step or reviewed pack metadata.
  • S2 Unicode normalization in exact-passage matching.
  • S3 Fix false amount conflicts.
  • S4 Robust date parsing for conflict checks.
  • S5 Harden production route access.
  • S6 Bound concurrency honestly.
  • S7 Defensive result rendering.
  • S8 Improve account form reliability.
  • S9 Make shell and state reset honest.
  • S10 Saved-case pagination and search.
  • S11 Validate pack registration and review metadata.
  • S12 Safe observability.
  • S13 Accessibility and mobile export.
  • S14 Review source snippet truncation.
  • S15 Preserve non-PII specificity in query planning.
  • S16 Keep fictional walkthrough clearly labeled.

Could-have

  • C1 Reviewed compensation formulas.
  • C2 Multilingual letter templates.
  • C3 Packs/jurisdictions with review workflow.
  • C4 Channel-specific filing assistance (checklists/reminders only, no auto-submission).
  • C5 Historical policy comparison.
  • C6 Image/OCR intake after live endpoint test.
  • C7 Release evidence (20+ runs, jurisdiction/compensation reviews).
  • C8 Accessibility enhancements.
  • C9 Observability dashboard.

Out-of-scope

  • O1 Automatic sending/filing/contacting.
  • O2 External complaint status tracking or polling.
  • O3 Legal advice, eligibility determinations, outcome probabilities.
  • O4 Compensation entitlement claims without reviewed formulas.
  • O5 Marking unreviewed applicability as supported.
  • O6 OCR/PDF or accounts expansion beyond current saved-case scope.
  • O7 Community complaint-pattern discovery.

4. Bottom line

The app is already close to the desired positioning. The critical work is to fix the baseline (build/lint/tests), close evidence-grounding holes, make applicability and remedy language unambiguous, and align docs with the implemented saved-case features. Everything that would turn it into a filing service—auto-submission, external tracking, legal advice—should remain out of scope.
